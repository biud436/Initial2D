# 검수 계획: 테스트 전략과 단계별 게이트

**권장 모델**: 검수 인프라 구축(러너, 골든 이미지 체계, 결정성 확보)은 Claude Fable 5 — 로드맵 전체의 품질이 이 설계에 걸려 있다. 이후 개별 테스트 추가는 Opus 5.

> 검수는 아홉 번째 단계가 아니다. **모든 단계(1~8)의 완료 조건에 내장되는 교차 절차**이며, 이 문서는 그 방법을 정의한다.
> 원칙은 하나다: 어떤 단계도 자동화된 검증 없이는 ✅로 바꿀 수 없다.

## 1. 검수 원칙

1. **완료의 정의에 테스트가 포함된다.** 각 단계 문서의 "완료 기준"은 이 문서의 단계별 검수 매핑(7절)을 통과해야 충족된 것으로 본다.
2. **버그는 테스트를 남긴다.** 버그를 고칠 때는 그 버그를 재현하는 테스트를 먼저 추가하고, 고친 뒤 통과를 확인한다.
3. **자동과 수동을 구분한다.** 회귀는 기계가 잡고, 손맛(이동감, 타자 속도, 폰트 가독성)은 사람이 본다. 수동 검수 항목은 체크리스트로 문서화해 매번 같은 눈으로 본다.
4. **회귀 스위트는 항상 전부 돈다.** 5단계를 작업하다가 1단계 기능을 깨뜨리는 것을 막는 것이 검수의 절반이다. 플래피버드가 계속 돌아가는지가 범용성 회귀의 기준점이다.

## 2. 이미 있는 토대 (재사용)

| 자산 | 내용 | 활용 |
|---|---|---|
| `tests/run_engine_tests.py` | 픽셀 검증 스위트 | 골든 스크린샷 러너의 뼈대로 확장 |
| `INITIAL2D_SCREENSHOT`, `INITIAL2D_SCREENSHOT_FRAME`, `INITIAL2D_EXIT_AFTER` | N프레임 실행 후 스크린샷과 종료 | CI에서 씬 단위 캡처 |
| `AUTOPLAY` 전역 (`INITIAL2D_AUTOPLAY`) | 씬이 스스로 조작을 재생 | 자동 플레이 시나리오의 시작점 |
| 고정 타임스텝 (16ms 고정 delta, `AppSDL2.cpp`) | 프레임 수 = 게임 시간 | **결정적 재생의 핵심 전제.** 같은 입력 시퀀스는 항상 같은 결과 |
| `phase0_sanity`, `phase1_sanity` | 의존성 없는 C++ 검증 실행 파일 | C++ 단위 테스트 스타일의 선례 |

InitialEditor 저장소에는 테스트가 전무하다. 이번 로드맵에서 처음 도입한다 (3.5절).

## 3. 테스트 계층

### 3.1 C++ 단위 테스트

- 대상: 순수 로직만. gid 해석과 아틀라스 좌표 계산(2단계), 맵 JSON 파싱, UTF-8 변환, BMFont 파싱('힣' 경계 포함), `NormalizePath`, collision 조회.
- 방식: 기존 sanity 실행 파일 스타일을 유지한다 (외부 프레임워크 없이 assert 헬퍼, 저장소의 최소 의존 철학과 일치). 파일당 하나의 실행 파일이 아니라 `engine_unit_tests` 타겟 하나에 모은다.
- 실행: `cmake --build build && ./build/engine_unit_tests`가 exit code로 성패를 알린다.

### 3.2 Lua 단위 테스트 (헤드리스)

RPG 프레임워크는 대부분 Lua이므로 여기가 검수의 중심이다.

- 대상: 엔진 없이 검증 가능한 순수 로직 — 이동 큐와 충돌 판정(5단계), 코루틴 인터프리터의 트리거와 잠금과 병렬 실행(6단계), 줄바꿈 계산(7단계), 이동 루트 파서.
- 방식: `scripts/rpg/` 모듈은 엔진 전역(`Input`, `Sprite`, `Tilemap` 등)을 직접 부르지 않고 **주입받은 테이블을 통해 부르도록 작성**한다. 테스트는 가짜 테이블(예: 항상 통행 가능한 맵, 정해진 키 입력)을 주입한다. 이 규칙은 5, 6, 7단계 구현 시 강제한다.
- 러너: `tests/lua/run_tests.lua`. 엔진 바이너리로 실행해 Lua 버전 불일치를 없앤다. 헤드리스 실행은 `SDL_VIDEODRIVER=dummy`로 시도하고, 소프트웨어 렌더러 폴백이 안 되면 창을 띄우되 `INITIAL2D_EXIT_AFTER`로 즉시 종료한다 (인프라 구축 시 검증할 것).

### 3.3 골든 스크린샷 회귀

- 각 단계의 데모 씬마다 골든 이미지를 `tests/golden/`에 둔다. 러너는 씬을 지정 프레임까지 돌리고 캡처해 골든과 비교한다.
- 비교는 완전 일치가 아니라 **허용 오차(다른 픽셀 비율 임계값)**를 둔다. 플랫폼과 드라이버별 미세 차이를 흡수하되, 임계값은 낮게 시작해 실제 소음을 보고 조정한다.
- 골든 갱신은 의도적 절차로만: `--update-golden` 플래그로 갱신하고, 갱신된 이미지는 커밋 전에 눈으로 확인한다. "테스트가 깨져서 골든을 갱신했다"는 커밋 메시지에 이유를 남긴다.
- 최소 골든 목록: 플래피버드 플레이 중 화면(범용성 기준점), 타일맵 스크롤 씬(2단계), 캐릭터 걷기 씬(5단계), 대화창 전체 표시 상태(7단계), 데모 마을 첫 화면(8단계).

### 3.4 자동 플레이 시나리오 (E2E)

- `AUTOPLAY`를 "씬이 알아서 논다"에서 **"입력 시퀀스를 프레임 단위로 재생한다"**로 확장한다: `tests/scenarios/*.lua`에 `{ frame = 120, key = "RIGHT", state = "down" }` 형태의 시퀀스를 정의하고, 재생기가 `Input`을 대신해 주입한다 (3.2의 주입 구조를 재사용).
- 고정 타임스텝 덕분에 같은 시퀀스는 같은 결과를 낸다. 시나리오 끝에서 상태를 검증한다 (플레이어 위치, 진행 플래그, 최종 화면 골든 비교).
- 핵심 시나리오: "마을에서 정해진 경로로 걷기 → NPC에게 말 걸기 → 선택지 2번 → 분기 대사 확인 → 집에 들어갔다 나오기" (8단계의 인수 테스트).

### 3.5 브리지, 에디터, 포맷 계약 테스트

- **브리지 서버** (`tools/bridge/`): Node 내장 `node:test`로 API를 테스트한다. 필수 항목: 화이트리스트 밖 경로 거부, `..`와 URL 인코딩(`%2e%2e`) 경로 탈출 차단, PUT 후 GET 왕복 일치, 127.0.0.1 외 바인드 없음.
- **포맷 계약**: 맵 포맷 v1 샘플 픽스처를 `tests/fixtures/maps/`에 두고 **양쪽이 같은 파일을 검증한다.** 엔진 쪽은 "픽스처를 로드해 다시 직렬화하면 동등하다"(라운드트립), 에디터 쪽은 "내부 상태로 불러와 내보내면 동등하다". 포맷이 바뀌면 픽스처를 먼저 바꾸고 양쪽 테스트가 함께 깨지는 것을 확인한다 — 이것이 두 저장소의 어긋남을 막는 장치다.
- **에디터 단위 테스트**: vitest를 도입하되 범위를 좁게 시작한다 — 전역 타일 ID → gid 변환기, MapSchema 직렬화, 역직렬화. 렌더링(PIXI)은 이번 로드맵에서 테스트하지 않는다.

## 4. 결정성 확보 규칙

자동 플레이와 골든 비교가 성립하려면 실행이 결정적이어야 한다.

- `math.random`은 반드시 시드를 받는 래퍼(`rpg.rng`)를 통해 쓴다. NPC 배회(5단계)가 첫 적용 대상. 테스트는 시드를 고정한다.
- 프레임 카운트 기반으로만 시간을 잰다. 벽시계(`os.time` 등)를 게임 로직에 쓰지 않는다.
- 애니메이션과 타자 효과 속도는 프레임 수 기준으로 정의한다.
- **테스트 씬에서 Lua 쪽 카운터로 상태를 전환하지 않는다.** 고정 스텝 루프라 `Update`는 렌더 프레임당 0~N회 실행되어 스크린샷 프레임 번호와 어긋난다 (2단계에서 실측: 시작 스터터 중 렌더 12프레임에 업데이트 20회 이상). `GetFrameCount()`도 초마다 리셋되는 값이라 대안이 못 된다. 캡처할 상태는 환경 변수로 고정하고 러너가 씬을 상태별로 여러 번 실행한다 (`tilemap_scene.lua`의 `INITIAL2D_TEST_CAM` 방식).

## 5. 플랫폼 매트릭스

| 플랫폼 | 자동 (매 작업) | 수동 (단계 완료 시) |
|---|---|---|
| macOS | 전체 스위트 (단위 + 골든 + 시나리오) | 데모 플레이스루 |
| Android | 빌드 성공 확인 | 기기에서 체크리스트 (터치 조작, 화면 비율, 수명 주기). 조작 확인은 `adb shell input swipe x y x y <ms>`(홀드)와 `input keyevent --longpress`로 한다 — 한 프레임보다 짧은 합성 입력은 엔진이 놓친다 (02-tilemap.md 구현 노트) |
| Windows GDI | 대상 아님 (아카이브, 무수정 원칙) | — |

CI는 GitHub Actions macOS 러너에서 "빌드 → 단위 → 골든 → 시나리오"를 돌리고 실패 시 스크린샷을 아티팩트로 남긴다. 브리지와 에디터는 Node CI로 별도 잡을 둔다. CI 구성은 인프라 체크리스트(9절)에 포함하되, 로컬에서 같은 명령 한 줄(`make test` 또는 `tests/run_all.sh`)로 전부 돌 수 있는 것이 우선이다.

## 6. 수동 검수

자동화가 못 잡는 것들은 단계 완료 시 체크리스트로 본다. 각 단계 문서의 완료 기준 중 "자연스럽다", "부드럽다", "가독성" 항목이 여기 해당한다.

- 검수 세션은 결과를 남긴다: `docs/plans/index.md` 진행 표의 메모 칸에 날짜와 발견 사항 한 줄.
- 발견된 문제는 즉시 고치지 않더라도 해당 단계 문서의 체크리스트에 `- [ ]`로 추가해 잊지 않는다.

## 8. 검수 게이트 (단계 완료 절차)

단계를 ✅로 바꾸기 전에 순서대로:

1. 이 단계에서 추가된 기능마다 대응하는 자동 테스트가 존재하는가 (7절 매핑 기준)
2. 전체 회귀 스위트가 통과하는가 (이전 단계 테스트 포함, 플래피버드 포함)
3. 골든 스크린샷이 추가 또는 갱신되었고 눈으로 확인했는가
4. 수동 검수 체크리스트를 수행하고 결과를 진행 표 메모에 남겼는가
5. `docs/plans/index.md`와 해당 단계 문서의 체크리스트를 갱신했는가

## 10. 자율 검증 루프 (AI 에이전트의 작업 방식)

이 로드맵의 구현은 대부분 AI 에이전트(Claude)가 수행한다. 사람이 매번 확인해 주기를 기다리는 것이 아니라, **에이전트가 스스로 실행하고 스스로 확인하는 루프**를 돌아야 한다. 앞 절들의 검수 체계가 전부 "CLI 한 줄, exit code, 기계가 읽을 수 있는 출력"으로 설계된 이유가 이것이다.

### 기본 루프

```
체크리스트 항목 하나 선택
  → 구현 (작은 diff)
  → 빌드 (cmake --build build)
  → 관련 테스트만 먼저 실행 (빠른 피드백)
  → 전체 스위트 (tests/run_all.sh)
  → 실패: 출력을 읽고 원인을 수정한 뒤 루프 재진입
  → 성공: 단계 문서 체크리스트 갱신, 다음 항목
```

- **유한 실행 보장.** 게임 실행 확인은 반드시 `INITIAL2D_EXIT_AFTER`와 조합한다. 종료되지 않는 프로세스를 띄워 놓고 기다리는 상황을 에이전트 스스로 만들지 않는다.
- **시각 검증도 루프 안에 있다.** `INITIAL2D_SCREENSHOT`으로 캡처한 PNG를 에이전트가 직접 읽어 "대화창이 실제로 화면 하단에 그려졌는가" 같은 의미 수준의 확인을 한다. 골든 비교(픽셀 일치)와 에이전트의 눈(의미 확인)은 서로 보완 관계다.
- **상태 검증은 stdout으로.** 시나리오 재생이 끝나면 검증 결과를 `print`로 남기고, 러너가 이를 exit code로 변환한다. 에이전트는 로그를 읽고 다음 행동을 정한다.

### 가드레일 (루프가 지켜야 할 것)

1. **테스트를 약화시켜 통과시키지 않는다.** assert 삭제, 골든 오차 임계값 완화, 시나리오 검증 축소는 수정이 아니라 회피다. 그것이 정말 필요하다고 판단되면 루프를 멈추고 이유를 보고한 뒤 사용자 승인을 받는다.
2. **같은 실패에 같은 종류의 수정이 세 번 연속 실패하면 멈춘다.** 접근 자체가 틀렸을 가능성이 크다. 원인 분석을 남기고 계획 문서를 갱신하거나 사용자에게 판단을 넘긴다.
3. **전체 스위트가 통과하기 전에는 완료를 보고하지 않는다.** "구현은 끝났는데 테스트는 아직"은 완료가 아니다.
4. **골든 갱신을 루프 안에서 자동으로 하지 않는다.** 렌더링이 의도적으로 바뀐 경우에만, 갱신 전후 이미지를 나란히 확인하고 이유를 남긴 뒤 갱신한다.
5. **손맛 검수는 사람 몫으로 남긴다.** 8절 게이트의 수동 항목(이동감, 타자 속도, 가독성)은 에이전트가 스크린샷과 시나리오 결과를 근거 자료로 제시하고, 최종 판정은 사용자가 한다.

### 세션을 넘는 루프

- **진행 상태는 대화가 아니라 문서에 있다.** 세션이 바뀌어도 `index.md`의 진행 표와 각 단계 문서의 체크리스트가 루프의 현재 위치다. 루프를 재개하는 에이전트는 거기서 시작한다.
- **작업 중 발견한 문제는 즉시 해당 단계 문서에 체크리스트로 적는다.** 에이전트의 기억이 아니라 문서가 백로그다.
