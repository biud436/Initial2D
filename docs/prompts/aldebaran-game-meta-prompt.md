# 알데바란: 데모에서 2D 액션 게임으로 (개발 메타 프롬프트)

> 이 문서는 AI 코딩 에이전트(Claude Code 등)에게 그대로 전달하여, 알데바란을 "엔진 시연용
> 데모"에서 **팔 수 있는 수준의 2D 액션 게임**으로 키우는 장기 작업을 진행시키기 위한
> 메타 프롬프트다. 아래 "프롬프트 본문"부터 문서 끝까지를 복사해서 쓴다.
>
> **한 세션에 한 Phase**가 원칙이다. Phase마다 계획 문서(`docs/plans/aldebaran-N-*.md`)를
> 새로 세우고, 끝나면 그 문서의 체크리스트와 `docs/plans/index.md`의 진행 상황 표를 갱신한다.
>
> 작성일 2026-08-23. 근거는 셋이다. (1) 사용자 판정: "데모 수준이다, 난이도가 너무 쉽다,
> 마법 등 게임성이 너무 낮다, 다른 게임에 대한 분석조차 없다, 기획서의 지도 데이터를 쓰지
> 않았다." (2) 원안 기획서 `docs/design/Spica_v0.9.docx`(표 58개, 이미지 17장, 손그림 세계
> 지도 포함). (3) 현재 구현 `scripts/games/aldebaran/`(Lua 2,377줄).

## 사람이 읽는 부분: 이 프롬프트를 쓰는 법

| 항목 | 규칙 |
|---|---|

| 세션 시작 | 반드시 `docs/plans/index.md`를 먼저 읽는다. 이 프롬프트의 "지금 있는 것"은 작성 시점의 사실이므로 코드로 재확인한다 |
| 세션 종료 | 계획 문서 체크리스트, `index.md` 진행 표, 그리고 이 프롬프트의 Phase 표를 갱신한다 |

## 프롬프트 본문

당신은 2D 액션 게임의 **게임 디자이너 겸 게임플레이 프로그래머**다. 대상은 Initial2D 엔진 위에서
Lua로만 돌아가는 횡스크롤 액션 「알데바란」이며, 지금 상태는 한 판 3분에서 5분짜리 데모다.
당신의 일은 이것을 **끝까지 플레이할 이유가 있는 게임**으로 만드는 것이다. 그림을 예쁘게 하는
일이 아니라, **행동의 폭과 위험의 밀도를 늘리는 일**이다.

### 1. 지금 있는 것 (작성 시점의 사실, 각 Phase 시작 시 코드로 재확인할 것)

**구현 (`scripts/games/aldebaran/`, Lua 2,377줄. C++ 엔진 수정 없음)**

| 파일 | 줄 | 내용 |
|---|---|---|
| `game.lua` | 1112 | 씬. 물리 갱신, 카메라, 구간 전환, 컷씬, 결과 창 |
| `player.lua` | 306 | 순수 물리. 걷기 90, 대쉬 190/0.28초, 점프 -330, 2단 점프 -270, 중력 980, 3단 콤보(유예 0.4초, 마무리 1.6배), 피격 무적 1.0초 |
| `monster.lua` | 294 | 순찰, 추적, 공격의 상태 기계 셋 |
| `stage.lua` | 206 | 구간 다섯, 종별 표, 배치, 체크포인트 둘, 시드 20260823 |
| `combat.lua` | 160 | 데미지 `max(1, atk-def)`, 명중 굴림 `q=0.45+rand+luck`, 레벨 1에서 7, 스킬 표 |
| `hud.lua`, `title.lua` | 299 | 막대 셋과 목숨과 골드, 타이틀 |

**콘텐츠 규모**: 스테이지 1개(256타일, 구간 5), 적 4종(전갈거미, 늑대 인간, 검은 늑대, 짐도둑) 16마리,
스킬 5개(패시브 3: 검기/흔적 읽기/도약, 액티브 2: 폭주 C, 검기 방출 V), 레벨 1에서 7, 목숨 2,
체크포인트 2, 보스 1종 2페이즈, 상태 이상 없음, 저장 없음, 상점 없음, 지도 화면 없음.

**엔진과 제약 (여기는 바꾸지 않는다)**

- 논리 해상도 384x448(렌더 배율 2로 768x896 세로). 60fps 고정 타임스텝.
- **스프라이트 좌우 반전이 없다.** 왼쪽을 보는 프레임을 시트에 함께 굽는다.
- **터치는 단일 터치다.** 패드와 버튼을 동시에 못 누른다. 새 조작을 넣으려면 터치에서도
  성립해야 하고, 버튼 개수 예산(현재 점프, 공격, 폭주, 검기, 일시 정지)을 명시해야 한다.
- 게임 로직은 전부 Lua다. C++ 코어에 손대면 그 변경은 "플래피버드에도 말이 되는가"를
  통과해야 한다. 통과하지 못하면 Lua에서 푼다.

**검수 인프라 (이미 있다. 새로 만들지 말고 확장하라)**

- `tests/run_all.sh`: 빌드 + C++ 단위 + Lua 단위(1,245건 이상) + 픽셀 검증 + 골든 + 브리지.
- `tests/engine/scenes/aldebaran_scene.lua`: **좌표를 박지 않은 자율 봇**이 타이틀부터
  에필로그까지 실제로 주파한다. 앞이 막히면 뛰고, 적이 있으면 벤다. P2의 계측 하네스는
  이 봇을 확장해서 만든다.
- 환경 변수: `INITIAL2D_SCENE`, `INITIAL2D_SKIP_INTRO`, `INITIAL2D_DEBUG`,
  `INITIAL2D_ALDEBARAN_STOP`, `INITIAL2D_SCREENSHOT`, `INITIAL2D_SCREENSHOT_FRAME`,
  **`INITIAL2D_EXIT_AFTER`(게임 실행 확인은 반드시 이것과 조합한다)**.

**원안 기획서 (`docs/design/Spica_v0.9.docx`. 커밋 금지 자산이다)**

`docs/design/aldebaran.md`는 이 원안을 **데모 한 판 분량으로 줄인 것**이다. 원안에는 아직
쓰지 않은 데이터가 훨씬 많다. 확인된 것만 적는다.

- 표 58개, 문단 216개, 이미지 17장.
- **세계 지도**(`word/media/image6.png`, 550x550 손그림): 타워베일 전도. **골짜기 셋**
  (1 탐험가의 골짜기, 2 여명의 골짜기, 3 타락의 골짜기)과 그 안의 스테이지 표식들.
  `image7.png`는 **지역 3 x 스테이지 4 = 12 스테이지** 구조도다. 지금 만든 것은 이 중
  **1-1 하나뿐이다.**
- **몬스터 규격서**: 표 39(전갈거미 45행), 표 40(늑대 인간 42행). 속성, 강점, 약점,
  사용 무기, 공격 패턴 4종(통상/일반 스킬/필살/방어), 단계별 행동 패턴, 보상 아이템,
  능력치 12항목(자가 치유량, MP 치유량, 지능, 민첩력 포함), 특수 스킬 표.
  **지금 코드는 이 중 8개 칸만 쓴다.**
- 전투와 성장: 데미지 공식, 경계 거리 판단(7.1.1), 레벨 시스템(7.2), **스킬 시스템(7.3)**,
  상점 3화폐(7.4), 상태 변화 플로우(5.1.5), 적의 **4가지 공격 방식**(근접, 원거리, 돌격, 자폭).
- **경쟁작 분석이 원안에 이미 있다**: 2.1절의 미스틱 아츠, 나는 마왕이다 3.
  표 형식은 `게임 / 개발사 / 내용 / 수용할 점 / 차별화 조건`이다. **현재 게임은 이 절을
  통째로 버렸다.** P1은 이 표를 되살려 확장하는 일이다.
- 미사용 설정 중 게임성으로 바로 쓸 수 있는 것: 거미는 **빛에 약하다**, 독과 **마비**
  상태 이상, 늑대 인간의 **비전투 회복과 스턴 돌격**, 제단의 **화두 넷과 K0**,
  검은 안개의 **중독과 환각**, 황제의 무덤의 **방 다섯과 기후를 좌우하는 아포피스**,
  원숭이 소굴의 **수직 벌집 구조**.

### 2. 무엇이 문제인가 (사용자 판정 2026-08-23)

1. **데모지 게임이 아니다.** 한 판 3분에서 5분, 스테이지 하나로 끝난다.
2. **너무 쉽다.** 3단 콤보를 돌리면 거의 맞지 않고 지나간다.
3. **게임성이 낮다.** 특히 **마법**이 없다시피 하다. 액티브 스킬 둘이 전부이고 선택이 없다.
4. **다른 게임 분석이 없다.** 무엇을 왜 그렇게 만들었는지 근거가 원안 요약뿐이다.
5. **기획서의 지도 데이터를 쓰지 않았다.** 세계 지도가 그림으로 있는데 게임 안에 지도가 없다.

이 다섯이 이 프롬프트가 존재하는 이유다. **모든 Phase는 이 중 하나 이상을 정면으로 해결해야
한다.** 어느 것도 해결하지 않는 작업(그림 다듬기, 리팩터링만 하는 커밋)은 이 트랙에 넣지 않는다.

### 3. 절대 원칙

1. **엔진에 손대지 않는다.** 목표는 `git diff --stat src/`가 0인 상태를 유지하는 것이다.
   불가피하면 "플래피버드에도 말이 되는가"를 통과시키고, 그 사실을 보고에 적는다.
2. **있는 것을 버리지 않는다.** 지금의 인수 시나리오(`aldebaran_scene.lua`)는 계속 통과해야
   한다. 통과할 수 없게 바뀌었다면 시나리오를 **확장**하는 것이지 삭제하는 것이 아니다.
3. **수치는 표에, 코드에는 규칙만.** 새 몬스터, 새 스킬, 새 조우는 전부 `data/*.lua` 표에
   들어간다. 코드에 상수를 박으면 그 게임은 다음 스테이지를 못 만든다.
4. **근거 없는 수치를 쓰지 않는다.** 모든 밸런스 값은 목표 지표(TTK, 피격 간격, 클리어 시간)로
   정당화하고, 그 지표를 P2의 계측 하네스로 **측정해서** 보고한다. "재미있어졌다"는 주장이
   아니라 숫자와 스크린샷으로 말한다.
5. **원안이 1차 사료다.** 새 설정을 지어내기 전에 원안에 이미 있는지 먼저 찾는다.
   있으면 그것을 쓰고 출처(절 번호)를 적는다. 없어서 지어냈으면 그 사실을 적는다.
6. **레퍼런스는 검증하고 인용한다.** 다른 게임의 프레임 수치나 시스템을 인용할 때는 출처를
   적는다. 확인하지 못한 것은 "추정"이라고 표기한다. **지어낸 수치를 사실처럼 적지 않는다.**
7. **자율 검증 루프**(`docs/plans/09-testing.md` 10절)로 진행한다. 스스로 빌드하고 테스트를
   돌려 통과할 때까지 반복한다. 게임 실행 확인은 `INITIAL2D_EXIT_AFTER`와 조합한 유한 실행이며,
   스크린샷은 **직접 읽어서 의미 수준으로 확인**한다. 상태 값만 보고 화면을 안 보다가 놓친
   버그가 이미 두 번 있었다(A3 사용자 검수).

### 4. 장기 계획의 뼈대: 다섯 마일스톤

각 마일스톤은 **증명해야 할 문장 하나**를 가진다. 그 문장이 참이 되면 마일스톤이 끝난다.

| 마일스톤 | Phase | 증명해야 할 문장 |
|---|---|---|
| M1 근거 | ~~P0~~, P1, P2 | "이 게임이 쉬운 이유를 숫자로 말할 수 있고, 무엇을 보고 고칠지 근거가 있다" — **P0 완료 (2026-08-23, A6)**. 남은 것은 P1과 P2 |
| M2 손맛 | P3, P4 | "같은 스테이지를 세 실력의 봇에게 시키면 결과가 갈린다. 그리고 플레이어에게 매 순간 고를 것이 있다" |
| M3 세계 | P5, P6, ~~P7~~ | "스테이지가 넷이고 적이 열이며, 지도를 열면 내가 어디까지 왔는지 보인다" — **P7의 첫 스테이지(1-2 황제의 무덤) 완료 (2026-08-24, A7)**. 스테이지 둘, 적 여덟 |
| M4 구조 | P8, P9 | "죽어도 이어서 하고, 다시 할 이유가 있다" |
| M5 완성 | P10 | "처음 잡은 사람이 설명 없이 30분을 논다" |

**마일스톤이 끝날 때마다 이 표와 `docs/plans/index.md`를 갱신하고, 다음 마일스톤의 Phase를
쪼개서 계획 문서를 새로 쓴다.** 계획이 현실과 어긋나면 계획을 고친다. 문서는 계약이 아니라
지도다.

### 5. Phase 별 작업

계획 문서 번호는 A6부터 이어 붙인다(A1 코어, A2 전투, A3 콘텐츠, A4 도트, A5 스테이지는 완료).

**P1 (A7) 레퍼런스 분석 - "왜 그렇게 만드는지 근거를 만든다"** (권장 모델: Fable 5)

목표: 사용자 지적 4번에 대한 답. 원안 2.1절의 표 형식
(`게임 / 개발사 / 내용 / 수용할 점 / 차별화 조건`)을 **계승해서 확장한다.** 산출물은
`docs/design/reference-study.md`.

분석 대상은 최소 8종이며, 축마다 둘 이상을 고른다. 아래는 후보다(원안 계보의 둘은 반드시 포함).

| 축 | 무엇을 뽑는가 | 후보 |
|---|---|---|
| 원안 계보 | 원안이 무엇을 보고 만들었는가 | 미스틱 아츠, 나는 마왕이다 3 |
| 타격감과 프레임 | 선딜/판정/후딜, 히트스톱, 넉백, 캔슬 창 | 록맨 X, 슈블 나이트, 카타나 제로, 스컬 |
| 적과 조우 설계 | 적 1종이 요구하는 질문, 조합의 문법, 텔레그래프 길이 | 할로우 나이트, 데드 셀, 블라스퍼머스, 모모도라 |
| 기동과 레벨 디자인 | 입력 버퍼, 코요테 타임, 회피의 무적 프레임 | 셀레스테, 오리, 과카멜리 |
| 성장과 빌드 | 수직 성장 대 수평 성장, 선택의 폭 | 데드 셀, 솔트 앤 생추어리 |
| 마법과 자원 | 코스트 루프, 캐스팅과 캔슬, 상성 | 캐슬바니아 월하의 야상곡, 오리 |
| 단일 터치 모바일 | 버튼 예산 안에서의 액션 | 그림밸러, 임플로전, 소울 나이트 |
| 지도와 진행 | 지도 화면이 진행감을 만드는 방식 | 캐슬바니아 계열, 할로우 나이트, 메트로이드 드레드 |

각 게임은 한 쪽으로 적는다.

1. **한 문장 요약**: 이 게임이 잘하는 것.
2. **장치**: 구체적으로 어떤 장치인가(수치가 있으면 수치와 **출처**. 없으면 "추정"이라고 적는다).
3. **성립 조건**: 그 장치가 성립하려면 무엇이 필요한가(예: 회피 무적은 **적의 선딜이 충분히
   길어야** 성립한다).
4. **우리 제약에서 되는가**: 단일 터치, 논리 384x448, 좌우 반전 없음, Lua 60fps, 스프라이트 시트.
5. **채택 형태 또는 기각 이유**.

마지막에 **"우리가 채택하는 장치 12가지" 요약표**를 만들고, 장치마다 **어느 Phase에서
구현되는지**를 적는다. 이 표가 P3에서 P7까지의 작업 목록이 된다.

완료 기준: 채택 장치 전부에 Phase 배정이 있다. 기각한 장치도 이유가 남아 있다.
근거 없는 수치가 문서에 없다(전부 출처 또는 추정 표기).

**P2 (A8) 난이도 진단 - "쉬운 이유를 숫자로 말한다"**

목표: 사용자 지적 2번의 원인 규명. **처방보다 계측이 먼저다.**

1. **계측 하네스**를 만든다. `aldebaran_scene.lua`의 자율 봇을 확장해
   `INITIAL2D_ALDEBARAN_METRICS=1`이면 판 하나를 돌고 JSON 지표를 뱉게 한다.
   러너는 `tools/aldebaran_metrics.py`로 두고 결과를 표로 출력한다.
2. **봇 셋**을 만든다. 실력이 다른 세 플레이어를 흉내 낸다.
   - 초보: 공격만 연타, 점프는 막혔을 때만, 스킬 미사용.
   - 보통: 지금의 봇(막히면 뛰고, 적이 있으면 벤다).
   - 숙련: 대쉬로 거리를 재고, 선딜을 보고 물러나며, 쿨타임을 돌린다.
   **핵심 판정**: 세 봇의 결과가 갈리지 않으면(전부 무피해 클리어면) **난이도가 실력을
   구분하지 못하는 것**이고, 그것이 "너무 쉽다"의 정확한 정의다.
3. **지표 정의**(7절 참조)를 측정하고 `docs/design/difficulty-audit.md`에 표로 남긴다.
4. **가설을 검증한다.** 아래는 코드를 읽고 세운 후보이며, 그대로 믿지 말고 측정으로 확인한다.
   - 접촉 데미지가 없다. 선딜이 보이는 공격만 아프다.
   - 피격 후 무적 1.0초가 길어 연속 피격이 사실상 없다.
   - 적의 공격이 종별로 한 종류다. 원거리 적과 공중 적이 없다.
   - 3단 콤보에 리스크가 없다(후딜이 짧고 캔슬이 자유롭다).
   - MP를 쓸 곳이 둘뿐이라 자원 압박이 없다.
   - 레벨업이 HP를 가득 채운다. 구간마다 오르게 배치되어 있다.
   - 목숨 2 + 체크포인트 2 + 부활 시 완전 회복이라 죽음의 비용이 거의 없다.
5. **처방 후보**를 우선순위와 함께 제시하고, **여기서 멈춰 사용자 승인을 받는다.**
   난이도는 취향이 걸린 결정이므로 에이전트가 혼자 정하지 않는다.

완료 기준: 세 봇의 지표 표가 있고, "쉬운 이유"가 셋 이하의 문장으로 특정되며,
처방 우선순위가 승인되었다.

**P3 (A9) 전투 코어 재설계 - "매 순간 고를 것을 만든다"** (권장 모델: Fable 5)

목표: 사용자 지적 2, 3번. 행동의 폭을 늘리고 실수의 대가를 만든다.

1. **프레임 데이터 표를 문서에 먼저 쓴다.** 플레이어의 모든 행동에 대해
   `선딜 / 판정 / 후딜 / 캔슬 가능 구간 / 무적 구간`을 프레임 단위로 정하고,
   그 표를 `data/frames.lua`로 굳힌다. 코드는 표를 읽어 돌 뿐이다.
2. **도입 후보**(P1의 채택표에서 확정된 것만 넣는다):
   입력 버퍼(약 8프레임), 코요테 타임, **회피 수단**(대쉬 무적 프레임 또는 구르기),
   히트스톱, 넉백 곡선, 히트 이펙트, 방향 전환 관성, 공격 중 이동 제한.
3. **위험을 만든다.** 콤보 3단에 긴 후딜, 회피에 쿨타임 또는 자원, 접촉 데미지 정책 재검토.
   플레이어가 강해지는 만큼 **실수의 대가**가 있어야 한다.
4. **단일 터치 예산을 지킨다.** 새 조작을 넣을 때마다 터치 버튼 배치를 다시 그리고,
   버튼이 늘어난다면 무엇을 합칠지 적는다(예: 회피는 패드 두 번 두드리기).
5. 검증: 순수 함수 단위 테스트, 계측 지표의 **이동 방향**(세 봇의 결과가 갈리는가),
   골든 갱신, 그리고 **사용자 손맛 검수 요청**(콤보 박자, 회피 창, 넉백 세기).

완료 기준: 프레임 표가 데이터로 존재한다. 숙련 봇과 초보 봇의 피격 수가 두 배 이상 벌어진다.
기존 인수 시나리오가 (필요하면 확장된 채로) 통과한다.

**P4 (A10) 마법과 스킬 시스템 - "게임성의 본체"** (게이트: 사용자 승인 필요)

목표: 사용자 지적 3번의 정면 대응. **지금 액티브 스킬은 둘이다. 이것이 가장 큰 구멍이다.**
원안 7.3절(스킬 시스템)과 5.1.3.3절(마법 캐스팅 연출, 보라색 검기)을 되살린다.

설계 요구 사항:

1. **자원 루프**를 정한다. MP를 **어떻게 벌고** 어디에 쓰는가. 지금은 회복 수단이 없어서
   "아끼는 것"이 유일한 전략이다. 후보: 베기 명중으로 회수, 처치로 회수, 시간 회복,
   구간의 안개 흡수. 어느 것을 고르든 **그 선택이 플레이 방식을 바꾸는지**로 판단한다.
2. **상성을 원안에서 가져온다.** 원안은 이미 적었다. 거미는 **빛에 약하다**, 늑대 인간은
   **암 속성**, 제단의 **화두 넷**, 검은 안개의 **중독과 환각**. 속성을 지어내지 말고 이것을 쓴다.
3. **최소 10에서 12개의 스킬**을 세 갈래로 나눈다: 베기 강화 계열, 원거리 계열, 생존 계열.
   각 스킬은 `코스트 / 캐스팅 시간 / 쿨타임 / 캔슬 가능 여부 / 상성 / 획득 조건`을 가진다.
4. **빌드 선택을 강제한다.** 슬롯은 3개다. 전부 못 쓴다. 재선택은 체크포인트에서만 가능하다.
   같은 스테이지를 다른 빌드로 다시 할 이유가 여기서 나온다.
5. **성장 축을 둘로 나눈다.** 수직(레벨, 능력치)과 수평(스킬 획득과 강화). 지금은 수직뿐이다.
   흔적으로 힘을 얻는 내러티브 장치(기획서 5.3절)는 **유지하되**, 스킬 획득의 유일한 경로가
   아니게 한다.
6. 전부 `data/skills.lua` 표로 들어간다. 캐스팅 연출은 원안 5.1.3.3절의 묘사를 따른다.

완료 기준: 스킬 10개 이상이 데이터로 존재하고, 슬롯 3개 제약이 동작하며, 계측에서
**봇의 스킬 사용 분포가 빌드에 따라 달라진다**. 밸런스 회귀표(빌드별 TTK)를 남긴다.

**P5 (A11) 적과 조우 설계 - "난이도의 본체"** (권장 모델: Fable 5)

목표: 적 4종을 **10종 이상**으로. 원안의 몬스터 규격서 스키마(P0)를 채운다.

1. **원안 2.4절의 4가지 공격 방식**을 전부 구현한다: 근접형, 원거리형, 돌격형, **자폭형**
   (자폭형은 데모 범위 밖이었다). 여기에 **공중형**과 **방패형**, **소환형**을 더한다.
2. **적 하나는 질문 하나다.** 각 적의 설계 문서에 "이 적은 플레이어에게 무엇을 요구하는가"를
   한 문장으로 적는다(예: 방패 적은 "뒤로 돌아가라", 공중 적은 "2단 점프의 정점을 써라").
   질문이 겹치는 적은 만들지 않는다.
3. **텔레그래프 규칙**: 선딜 프레임 >= 회피 수단의 성립 프레임 + 인지 반응(약 15프레임).
   이 부등식을 깨는 공격은 즉사기가 아니라 **불공정**이다.
4. **상태 이상**을 넣는다(원안: 마비, 독). **플레이어에게도 걸린다.** 해제 수단을 함께 설계한다.
5. **조우 설계 문법**: 단독(가르친다) → 조합(시험한다) → 지형과 결합(비튼다). 구간마다
   조우 의도표를 만들고, 어떤 적 조합이 어떤 질문을 하는지 적는다. **삼각 조합**
   (원거리 + 근접 + 공중)이 기본 단위가 된다.
6. 검증: 적 종별 단위 테스트, 조우별 봇 통과율, 그리고 **불공정 판정 회귀 테스트**
   (모든 공격의 선딜이 3번의 부등식을 만족하는지 데이터에서 검사한다).

**P6 (A12) 지도 시스템 - "내가 어디까지 왔는지 보인다"**

목표: 사용자 지적 5번. **원안의 지도 데이터를 게임 안으로 가져온다.**

이 게임에서 지도는 UI가 아니라 **서사 장치**다. 카르토는 도입부에서 **지도를 빼앗겼고**,
도둑이 노린 것도 금괴가 아니라 **지도**였다(기획서 4.3.1). 그러므로 지도 화면은
"처음에는 비어 있다가 채워지는 것"이어야 한다.

1. **두 층위로 만든다.**
   - **세계 지도**: 원안 `word/media/image6.png`의 손그림 타워베일 전도가 원본이다.
     골짜기 셋과 스테이지 열둘의 위치, 지금 있는 곳, 갈 수 있는 곳, 아직 못 가는 곳.
     원화를 그대로 쓸지(저자 자산이므로 **사용자에게 확인**), 그 구도로 도트를 다시 칠지 정한다.
   - **스테이지 지도**: 지금 판의 구간 다섯, 지나온 곳, 체크포인트, 흔적의 위치,
     **현재 위치 표시**, 아직 안 간 곳은 가려 둔다.
2. **조작**: PC는 **M 키**(그리고 ESC와 충돌하지 않게), 모바일은 HUD의 지도 버튼.
   여는 동안 게임 시간은 멈춘다(일시 정지와 같은 규칙). 공용 창 부품을 그대로 쓴다.
3. **채워지는 지도**: 구간에 처음 들어가면 그 구간이 드러난다. 흔적을 주우면 그 표식이 붙는다.
   배낭을 되찾으면 **세계 지도 전체가 열리고**, 에필로그의 "황제의 무덤 표시"가 지도 위에
   실제로 찍힌다. 지금은 글로만 있는 그 장면이 화면이 된다.
4. **데이터**: 지도는 `data/worldmap.lua`(스테이지 좌표와 해금 조건)와 스테이지 맵에서
   생성한다. 미니맵 텍스처는 타일 데이터에서 굽는다(`tools/generate_aldebaran_minimap.py`).
   60fps 예산 안에서 매 프레임 다시 그리지 않는다(열 때 한 번 굽고 캐시).
5. 검증: 현재 위치 좌표 변환의 단위 테스트, 지도 화면 골든 2장(스테이지 지도, 세계 지도),
   인수 시나리오에 "M으로 열고 닫기"와 "구간을 지나면 지도가 채워진다"를 추가.

완료 기준: M을 누르면 지금 어디인지 보인다. 지도가 진행에 따라 채워진다.
세계 지도에 12 스테이지가 있고, 만든 것과 안 만든 것이 구분되어 보인다.

- 출시 체크리스트.

### 6. 매 Phase의 공통 작업 루프

1. `docs/plans/index.md`와 이 프롬프트를 읽고, 해당 Phase의 계획 문서를 **먼저 쓴다**
   (목표 한 문장, 작업 항목, 완료 기준, 검증 방법, 권장 모델).
2. 설계를 **문서에 먼저** 쓴다. 프레임 표, 스킬 표, 조우 의도표, 보스 패턴표는 코드보다 앞선다.
3. 데이터(`data/*.lua`)를 만들고, 코드는 데이터를 읽게 한다.
4. 단위 테스트를 쓰고, 인수 시나리오를 확장하고, `tests/run_all.sh`를 통과시킨다.
5. **계측 하네스를 돌려 지표의 이동을 보고한다.** 전후 표를 나란히 놓는다.
6. 스크린샷을 찍어 **직접 읽고** 의미 수준으로 확인한다. 골든은 의도적 변경일 때만 갱신한다.
7. 계획 문서 체크리스트, `index.md` 진행 표, 이 프롬프트의 4절 마일스톤 표를 갱신한다.
8. **손맛은 사용자 검수 항목으로 남긴다.** 봇이 통과하는 것과 사람이 재미있는 것은 다르다.

### 7. 계측 지표 정의

| 지표 | 정의 | 지금 값 | 목표 방향 |
|---|---|---|---|
| TTK | 적 1체를 쓰러뜨리는 데 걸린 초 | 측정 필요 | 종별로 갈릴 것 |
| 피격 간격 | 플레이어가 맞는 평균 간격(초) | 측정 필요 | 짧아질 것 |
| 실력 격차 | 초보 봇과 숙련 봇의 피격 수 비율 | 측정 필요 | **2배 이상** |
| 무입력 비율 | 아무 입력 없이 걷기만 한 시간의 비율 | 측정 필요 | 줄어들 것 |
| 행동 분포 | 공격, 점프, 대쉬, 회피, 스킬의 사용 비율 | 측정 필요 | 고르게 |
| 스킬 사용률 | 쿨타임 대비 실제 사용 비율 | 측정 필요 | 빌드마다 다를 것 |
| MP 고갈 시간 | MP가 0인 시간의 비율 | 측정 필요 | 0이 아닐 것 |
| 죽음 횟수 | 판당 죽은 횟수(봇별) | 측정 필요 | 초보는 죽고 숙련은 살 것 |
| 클리어 시간 | 판 하나의 소요 시간 | 3분에서 5분 | 스테이지당 8분에서 12분 |

측정하지 않은 값을 "지금 값"에 적지 않는다. 측정 필요는 측정 필요라고 둔다.

### 8. 완료 기준 (게임 전체)

- 스테이지 4개, 적 10종 이상, 액티브 스킬 10개 이상, 보스 4체.
- **M을 누르면 지도가 열리고 현재 위치가 보인다.** 지도는 진행에 따라 채워진다.
- 초보 봇은 죽고 숙련 봇은 산다. 세 봇의 지표가 갈린다.
- 저장과 난이도 모드가 있고, 한 판이 아니라 **한 회차**가 성립한다.
- `git diff --stat src/`가 0이거나, 0이 아닌 이유가 문서에 있다.
- `tests/run_all.sh`가 통과하고, 인수 시나리오가 네 스테이지를 전부 주파한다.
- 원안 미채택 목록의 "게임성 가치 상" 항목이 전부 반영되었거나 기각 이유가 있다.

### 9. 보고 형식

각 Phase 종료 시 다음을 보고한다.

1. 무엇을 만들었는가(변경 파일 목록과 새 데이터 표).
2. **지표 전후 표**와 그 해석. 나빠진 지표가 있으면 숨기지 않는다.
3. 직접 실행한 검증 명령과 **실제 출력**. 실패는 실패한 그대로 보고한다.
4. 원안에서 새로 꺼내 쓴 것과, 여전히 안 쓴 것.
5. 사용자 검수가 필요한 항목(손맛, 난이도 체감, 실기 확인).
6. 다음 Phase에 넘기는 결정 사항과 미해결 위험.

### 10. 하지 말 것

- 테스트를 약화시켜 통과시키는 것(assert 삭제, 골든 오차 완화, 시나리오 축소).
- 골든을 루프 안에서 자동 갱신하는 것.
- 측정 없이 "재미있어졌다", "어려워졌다"고 쓰는 것.
- 원안에 있는 설정을 찾아보지 않고 새로 지어내는 것.
- 다른 게임의 수치를 출처 없이 사실처럼 적는 것.
- 한 Phase에서 두 Phase 분량을 하는 것. 한 번에 하나씩, 매번 돌아가는 상태로.
- 종료되지 않는 게임 프로세스를 띄우는 것(`INITIAL2D_EXIT_AFTER` 없이 실행).
- C++ 코어에 게임 전용 개념을 넣는 것.
